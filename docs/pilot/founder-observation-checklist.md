# Founder and Facilitator Observation Checklist

Use only after launch clearance, for the exact approved pilot scope. Keep completed
notes in the approved private location, not in this repository. The checklist is an
observation aid, not an assessment of a student's intelligence, disability or effort.

## Before Each Session

- [ ] G01-G06 remain closed; correct staging deployment and artifact versions are recorded.
- [ ] Facilitator, technical responder, backup and engineering escalation contact are available.
- [ ] Rehearsed containment and current recovery evidence are accessible to authorised operators.
- [ ] Support windows, participant notice, end date and optional-feedback process are explained.
- [ ] Student uses their own Student account; nobody asks for credentials or verification links.
- [ ] Permission for brief observation notes is recorded; no audio/video/screen recording is on.
- [ ] Private note uses alias, session, first/return visit and broad device category only.
- [ ] Student knows they can pause, decline notes, request an adjustment or stop entirely.

## Observe Without Coaching the Result

| Area                        | What to notice                                                                          | Safe prompt / recording rule                                                                                                                |
| --------------------------- | --------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| Entry                       | Verification delays, access-gate confusion, mistaken workspace                          | "What are you trying to do next?" Never inspect a password or mailbox token.                                                                |
| Pauses                      | Where and why the student pauses                                                        | Ask whether they are reading, thinking, unsure or interrupted; a pause is not evidence of confusion by itself.                              |
| Controls                    | Labels misunderstood, slider/numeric mismatch, units overlooked, missing keyboard focus | "What do you expect this control to change?" Record the label and behaviour, not every entered value.                                       |
| Theory                      | Optional detail opened or skipped, text searched for after interaction                  | Ask whether enough explanation was available; skipping optional theory is not failure.                                                      |
| Challenge                   | Goal understood, feedback noticed, help needed                                          | Do not suggest a solution to improve completion statistics. Record assistance separately.                                                   |
| Repeated attempts           | Intended practice, unclear save status, repeated Submit clicks                          | Ask what prompted a retry; do not interpret repeats as incompetence or silently count them as independent users.                            |
| Navigation                  | Backtracking, missing next step, confusion about empty Simulation Lab                   | Note the route/label. Explain scope only after recording first-use behaviour, unless support is needed.                                     |
| Visual/simulation behaviour | Missing labels, frozen visual, inconsistent measurement, unexpected motion              | Current scope is the static pressure activity; no standalone simulation should launch. Report a misleading result, not speculative physics. |
| Assessment                  | Safe errors, unclear unit feedback, persistence after review                            | Do not read or copy private answers into notes. Stop on pre-submit answer exposure or suspected scoring corruption.                         |
| Accessibility               | Zoom, touch targets, focus, reading order, screen-reader feedback                       | Ask what adjustment would help without asking for a diagnosis. Do not exclude the participant from results.                                 |
| Questions                   | Questions about engineering, procedure or terminology                                   | Record a redacted paraphrase and section. Escalate technical accuracy questions to the reviewer.                                            |

Allow an initial independent attempt where the student is comfortable, then help when
requested. Mark task outcomes **independent**, **assisted**, **blocked** or **declined**.
Do not lead with "wasn't that clear?" or announce success before the student responds.
Do not coach formal assessment answers, award progress manually or ask a student to keep
using a potentially incorrect engineering result for research.

## Minimal Note Template

| Field                                         | Entry                                             |
| --------------------------------------------- | ------------------------------------------------- |
| Pilot alias / session / first or return visit | `[private]`                                       |
| Release / lesson / assessment version         | `[allowlist reference]`                           |
| Observation permission / device category      | `[private]`                                       |
| Page or section / broad task                  | `[no token-bearing URL]`                          |
| Observed behaviour                            | `[observable fact, not inferred ability]`         |
| Student's explanation                         | `[optional redacted paraphrase, with permission]` |
| Assistance and outcome                        | `[independent / assisted / blocked / declined]`   |
| Issue category / priority / issue ID          | `[private issue register reference]`              |
| Owner and next action                         | `[assigned privately]`                            |

Do not record raw input histories, submitted answers, exact grade histories or personal
browser content. If timing helps diagnose friction, use a coarse note such as "brief
pause" or "needed help after a pause" rather than surveillance-style event capture.

## Stop and Aftercare

- [ ] Pause immediately under the [incident process](pilot-incident-process.md) for a
      security/privacy issue, engineering error concern, exposed answers, major auth failure
      or inaccessible core task. Support takes precedence over observation.
- [ ] Capture only the safe error reference and affected version; avoid additional exposure.
- [ ] Offer optional feedback and explain how to report something later privately.
- [ ] Confirm sign-out on shared devices and explain next session/end date.
- [ ] Reconcile observations with permitted saved evidence; do not infer completion from time.
- [ ] Record unknowns and contradictory feedback, not only success stories.
- [ ] Triage concerns the same day, assign ownership, and check that retention/access rules apply.
