# Architecture and security assessment

Date: 13 October 2026. Bounded code, test and read-only staging metadata review; not a penetration test. No fixes or live policy changes were made.

## Actual data flows

1. **Identity:** `apps/web/src/features/auth/server.ts` reads HttpOnly, SameSite=Lax cookies (Secure in production runtime). `supabase-provider.ts` calls Supabase Auth `/user`, rejects unconfirmed identity, then reads authoritative profile status and database roles. It does not trust client role metadata. The profile must match the authenticated user and expose the expected `deleted_at` status. Route/server-action helpers enforce capabilities before operations. Recovery uses a signed purpose-bound ticket and server checks; actual delivered-mail behavior remains unverified.
2. **Dashboard/library:** authenticated route -> `student-dashboard/server-data.ts` -> ordinary user JWT REST/RPC -> owner filters/RLS -> DTO/model -> UI. `summary-queries.ts` pages full lesson/bookmark library while the dashboard keeps bounded recent summaries. Failed access does not become invented progress.
3. **Bookmarks:** `saved-lesson-action.ts` obtains the session and validates intent/slug -> `saved-lessons-server.ts` -> JWT-bound repository -> `0024` RPCs compare supplied owner with `auth.uid()`, check active account and exact published target. Advisory locking and a unique index prevent duplicate saves. Withdrawn items can be removed by owner identifier without exposing their title/slug.
4. **Assessments:** server action -> verified student -> owned attempt + published catalogue match -> `packages/database/src/attempt-persistence.ts` -> deterministic assessment-core scoring -> **service-role** persistence/RPC -> atomic score/progress/audit update -> owned review. Correct answers are withheld in delivered assessment projections; ordinary direct question/answer reads are restricted. The browser's score/awards are not the scoring authority. Assessment service-role GETs explicitly filter owner but bypass ordinary RLS: do not describe this as session-scoped persistence.
5. **Simulations/pilot progress:** trusted server validates runtime/challenge inputs and calls service-role persistence. `0023` checks/locks active subject; `0025` resolves exact simulation version and parent publication and guards persistence. Positive live standalone simulation delivery is not proven. Pure engineering/simulation packages separate calculation from UI and provide normal/boundary/fault tests.
6. **Governance/admin:** review and role actions use session-bound Supabase RPCs after role/capability checks. `0013` validates exact review/version/attestations; `0016` enforces reviewer assignments (with documented administrator exception); `0006` rejects self-author approval. `0018/0019` publication functions require matching evidence and staging scope. `0015` audits access changes and restricts owner-role changes. Staff invitations use server privileges; Stage 1 did not invoke them.

## Backend enforcement and presentation defense

`0023` intersects authenticated policies with current account status and guards trusted writes. `0024` owns bookmark authorization in PostgreSQL. Assessment/simulation transactions in `0007/0008/0019/0023/0025` protect status, idempotency, active subject and publication. `packages/database/src/authorization.ts` provides self/admin and authorized-cohort logic; platform-owner visibility does not automatically equal administrator access to every private student record.

`auth/account-boundary.tsx`, identity scopes and private response cache controls protect displayed state across delayed responses, visibility changes and tabs. These are additional UI defenses, not substitutes for backend permissions. The identity hash is a cache scope, not an authorization credential.

Fresh read-only metadata: 37/37 public tables have RLS enabled and 129 public policies exist. Counts do not prove every policy is correct, every function has safe grants, or runtime catalog definitions match all repository migrations. Service roles intentionally bypass RLS. All reads of private data must be traced to a verified principal; this review sampled critical paths, not every possible query.

## Academic provenance and governance

Policy `docs/content/academic-source-quality-policy.md` establishes governing requirements first for compliance/safety, manufacturer material for equipment claims, university texts for theory, then credible educational material. McGraw Hill is preferred when topic-appropriate and lawfully accessible, not automatic authority.

`packages/content-system/src/index.ts` validates source-selection rationale, preferred-publisher assessment, textbook edition/publisher/date, rights, section references, conflict metadata and traceability. It rejects unresolved source conflicts for approved/published lessons. `sources/fluid-pressure/openstax-college-physics.json` records a legally available Level 4 alternative and explains the absence of a registered lawful McGraw Hill edition. Penn State pressure material provides a second existing source; neither should be represented as a newly evaluated equivalent textbook. No new bibliographic recommendation or source approval was made in Stage 1.

Equivalent alternatives must be selected by relevant topic, author credentials, university adoption, edition traceability, depth and lawful access, with a recorded rationale. Missing page numbers or editions must remain missing; web sections are valid identifiers where pagination is unstable. Metadata validation cannot establish copyright permission or human technical accuracy. No chapters, figures, licensed files or private reviewer comments were copied.

The static pilot v0.4.0 approval/publication JSON records exist and are imported by `publication/review-records.ts`; they refer to earlier protected staging evidence. Older v0.3.0 changes-required reviews are not current v0.4.0 approvals. Stage 1 confirms the records and gates, not the external reviewer's identity/credentials. Wider catalogue and simulations require their own exact-version review evidence.
